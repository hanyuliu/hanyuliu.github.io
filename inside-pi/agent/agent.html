#Module: agent

A stateful wrapper around the agent loop. It keeps the conversation between runs, holds the steering and follow-up queues, owns the abort switch, and tells listeners about every event.

The loop from agent-loop keeps no state. Each call gets a conversation and a config, and forgets both when it returns. Something has to remember the conversation from one run to the next, hold the messages the user types while a run is going, and give the app one place to subscribe to events. That is Agent, in one file of about 600 lines.

Most of the class is plumbing. The interesting parts are small: two queues that the loop drains through its getSteeringMessages and getFollowUpMessages config functions, one AbortController per run, and a function that turns loop events into state. The conversation the app reads from agent.state.messages is built only from message_end events, so the app and the loop never write to the same array.

#Contracts

The state an app can read. messages and tools can also be assigned; the rest is set by the agent itself.

type AgentState = {
    systemPrompt: String,              // read-only: replayed from the system messages in `messages`
    model: Model,                      // used for future turns
    thinkingLevel: ThinkingLevel,      // "off" | "minimal" | ... | "max"
    tools: AgentTool[],                // assigning copies the array
    messages: AgentMessage[],          // the conversation; assigning copies the array
    isStreaming: Bool,                 // read-only: true until a run's agent_end listeners finish
    streamingMessage: AgentMessage?,   // read-only: the model's reply while it streams
    pendingToolCalls: Set<String>,     // read-only: ids of tool calls still running
    errorMessage: String?,             // read-only: from the last failed or aborted reply
}

type QueueMode = "all" | "one-at-a-time"

What you pass to the constructor. Only streamFn is required. Most fields are copied to public properties of the same name, so the app can change them later, and are handed to the loop on every run.

type AgentOptions = {

    prepareNextTurnWithContext: async fn(context, signal?) -> AgentLoopTurnUpdate? ?,

}

#prompt

Sourceagent.ts › Agent.prompt › Agent.normalizePromptInput

Starts a run with new messages. A string becomes one user message, with any images added after the text. Only one run can be active at a time.

async fn prompt(input, images?)
    if activeRun exists:
        throw Error("Agent is already processing a prompt. Use steer() or followUp() to
                     queue messages, or wait for completion.")
    messages = match input:
        a list:     input
        a message:  [input]
        a string:   [user message with text input, then images]
    runPromptMessages(messages)

#continue

Sourceagent.ts › Agent.continue

Starts a run without a new prompt. The loop refuses to continue from an assistant message, so when the conversation ends with one, continue looks in the queues for something to send instead.

async fn continue()
    if activeRun exists:
        throw Error("Agent is already processing. Wait for completion before continuing.")
    if messages is empty, or holds only system messages:
        throw Error("No messages to continue from")
    if the last message is from the assistant:
        queued = steeringQueue.drain()
        if queued is not empty:
            runPromptMessages(queued, skipInitialSteeringPoll = true)
            // why: (test: "continue() keeps $mode steering semantics for assistant-tail fallback")
            //      the loop polls steering at the start of a run. Without the skip, that poll
            //      would add the next steering message to this same request.
            return
        queued = followUpQueue.drain()
        if queued is not empty:
            runPromptMessages(queued)
            return
        throw Error("Cannot continue from message role: assistant")
    runContinuation()            // last message is user or toolResult: the loop picks up from it

#runPromptMessages

Sourceagent.ts › Agent.runPromptMessages › Agent.runContinuation › Agent.createContextSnapshot

Both kinds of run look the same: a lifecycle wrapper around one call into the loop. The loop gets a copy of the conversation and the tools, never the arrays in state.

async fn runPromptMessages(messages, options)
    runWithLifecycle(signal ->
        agentLoop.runAgentLoop(messages,
                               { messages: copy of state.messages, tools: copy of state.tools },
                               createLoopConfig(options),
                               emit = processEvents,
                               signal, streamFunction))

async fn runContinuation()
    runWithLifecycle(signal ->
        agentLoop.runAgentLoopContinue(copy of messages and tools, createLoopConfig(),
                                       processEvents, signal, streamFunction))

#runWithLifecycle

Sourceagent.ts › Agent.runWithLifecycle › Agent.finishRun

Creates the run: a fresh AbortController and a promise that waitForIdle returns. If the loop throws, the failure becomes a normal error reply. The run always ends in finishRun.

async fn runWithLifecycle(executor)
    if activeRun exists:
        throw Error("Agent is already processing.")
    activeRun = { promise, resolve, abortController: new AbortController() }
    state.isStreaming = true
    state.streamingMessage, state.errorMessage = none
    try:
        executor(abortController.signal)
    catch error:
        handleRunFailure(error, aborted = abortController.signal.aborted)
    finally:
        finishRun()

fn finishRun()
    state.isStreaming = false
    state.streamingMessage = none
    state.pendingToolCalls = empty set
    resolve activeRun.promise                // waitForIdle() returns now
    activeRun = none

#handleRunFailure

Sourceagent.ts › Agent.handleRunFailure

The loop turns model and tool errors into messages, so it rarely throws. When something does throw (for example a streamFn that throws instead of returning an error stream), the agent makes up an empty assistant reply and sends the events a normal failed turn would send.

async fn handleRunFailure(error, aborted)
    reply = assistant message {
        content: [empty text],
        stopReason: "aborted" if aborted else "error",
        errorMessage: error.message,
        usage: all zero,
    }
    processEvents(message_start{reply})
    processEvents(message_end{reply})          // adds reply to state.messages
    processEvents(turn_end{reply, toolResults: []})
    processEvents(agent_end{messages: [reply]})
    // note: no agent_start or turn_start of its own. In the usual case the loop sent them
    //       before it threw.

#createLoopConfig

Sourceagent.ts › Agent.createLoopConfig

Builds the config for one run. Most fields are copied from the agent's public properties. Three fields connect the loop back to the agent: the two queue functions, and prepareNextTurn.

fn createLoopConfig(options) -> AgentLoopConfig
    skip = options.skipInitialSteeringPoll
    return {
        model: state.model,
        reasoning: state.thinkingLevel, with "off" meaning none,
        hooks and stream options: copied from this agent,
        getSteeringMessages: async fn():
            if skip:
                skip = false
                return []                    // only the first poll is skipped
            return steeringQueue.drain(),
        getFollowUpMessages: async fn(): followUpQueue.drain(),
        prepareNextTurn: if either prepare hook is set, async fn(context):
            if prepareNextTurnWithContext is set:
                return prepareNextTurnWithContext(context, signal)
            return prepareNextTurn(signal)   // older form: gets no context
    }

#PendingMessageQueue

Sourceagent.ts › PendingMessageQueue

Both queues are this small class. The mode decides how much one drain takes. The mode can change at any time, and the next drain uses the new one.

class PendingMessageQueue(mode: QueueMode)
    messages = []

    fn enqueue(message):  messages.add(message)
    fn hasItems() -> Bool: messages is not empty
    fn peek() -> AgentMessage[]
        if mode is "all": return copy of messages
        return [messages[0]] if there is one, else []
    fn drain() -> AgentMessage[]
        taken = peek()
        remove taken from the front of messages
        return taken
    fn clear(): messages = []

#processEvents

Sourceagent.ts › Agent.processEvents

Every loop event goes through here. First it updates the state, then it calls each listener in the order they subscribed, and waits for each one before calling the next. The loop waits for this function, so a slow listener slows the run.

async fn processEvents(event)
    match event.type:
        message_start, message_update:
            state.streamingMessage = event.message
        message_end:
            state.streamingMessage = none
            state.messages.add(event.message)     // the only place the run adds to the conversation
        tool_execution_start:
            state.pendingToolCalls = copy with event.toolCallId added
        tool_execution_end:
            state.pendingToolCalls = copy with event.toolCallId removed
            // note: a new Set each time; the old one is never changed
        turn_end:
            if event.message is an assistant reply with an errorMessage:
                state.errorMessage = event.message.errorMessage
        agent_end:
            state.streamingMessage = none
    if no run is active:
        throw Error("Agent listener invoked outside active run")
    for each listener in listeners, in subscribe order:
        await listener(event, activeRun.abortController.signal)

#abort and waitForIdle

Sourceagent.ts › Agent.abort › Agent.waitForIdle

abort fires the current run's signal. It does not stop anything by itself: the loop, the model stream, and the tools all watch the signal and stop on their own. The queues are left as they are.

fn abort()
    activeRun?.abortController.abort()        // does nothing when idle

fn waitForIdle() -> Promise
    return activeRun.promise if a run is active, else a resolved promise
    // note: the promise resolves in finishRun, after the agent_end listeners have finished

#reset

Sourceagent.ts › Agent.reset

Clears the conversation and both queues, but keeps the current system prompt and tools. It folds every system message in the conversation into one, so the reset conversation starts with the same prompt and tools the model saw last.

fn reset()
    if activeRun exists:
        throw Error("Agent is already processing. Wait for completion before resetting.")
    baseline = transcript.getCurrentSystemMessage(state.messages)
    state.messages = [baseline] if there is one, else []
    state.isStreaming = false
    state.streamingMessage, state.errorMessage = none
    state.pendingToolCalls = empty set
    clear both queues

#createMutableAgentState

Sourceagent.ts › createMutableAgentState

Sets up the state when the agent is built. The system prompt and tools from initialState become the first message of the conversation, unless the messages already start with a system message.

fn createMutableAgentState(initialState) -> MutableAgentState
    tools = copy of initialState.tools or []
    messages = copy of initialState.messages or []
    first = transcript.createInitialSystemMessage(initialState.systemPrompt, tools as declarations)
    if messages[0] is not a system message and first exists:
        put first at the start of messages
    return {
        systemPrompt: computed each time as transcript.getCurrentSystemPrompt(messages),
        model: initialState.model or a placeholder model with id "unknown",
        thinkingLevel: initialState.thinkingLevel or "off",
        tools, messages: setters copy the array they are given,
        isStreaming: false, pendingToolCalls: empty set,
    }

#peekQueuedMessages

Sourceagent.ts › Agent.peekQueuedMessages › Agent.hasQueuedMessages

Shows what the next turn would get, without removing it. Steering always comes first.

fn peekQueuedMessages() -> AgentMessage[]
    steering = steeringQueue.peek()
    return steering if it is not empty, else followUpQueue.peek()

fn hasQueuedMessages() -> Bool
    return steeringQueue.hasItems() or followUpQueue.hasItems()

#Rules

MUST     allow at most one active run at a time      // prompt, continue, and reset throw otherwise
MUST     give the loop a copy of messages and tools, never the arrays in state
MUST     add a message to state.messages only on message_end
MUST     call listeners in subscribe order, and wait for each one before the next
MUST     keep isStreaming true until every agent_end listener has finished
MUST     turn an error thrown by the loop into an assistant reply with stopReason "error"
         (or "aborted" if the run's signal was aborted), and still emit message, turn_end, agent_end
MUST     deliver steering messages before follow-up messages
MUST     drain one message per poll in "one-at-a-time" mode, and the whole queue in "all" mode
MUST NOT clear the queues when a run ends, fails, or is aborted     // only reset and clear*() do
MUST NOT continue from an assistant message unless a queue has something to send
MUST     keep the current system prompt and tools when reset() clears the conversation
SHOULD   create a new pendingToolCalls set on every change, instead of changing the old one

#Notes

There are two copies of the conversation during a run. The loop works on its own copy, which prepareNextTurn can replace (for example after compaction). state.messages grows only from message_end events. A host that replaces the loop's conversation has to set state.messages itself. AgentSession in the coding agent does this whenever the session file changes, by assigning the session's projection to agent.state.messages.

steer and followUp only queue a message. When it reaches the model depends on the loop: steering goes in after the current turn's tools finish, and follow-ups go in when the loop would otherwise stop (see runLoop in agent-loop). In the pi terminal app, Enter while the agent is working queues a steering message, Alt+Enter queues a follow-up, and Escape aborts.

Aborting does not clear the queues. The coding agent clears them itself (clearQueue) when it wants queued text back in the editor.
