#Module: agent-loop

The loop at the center of Pi. It sends the conversation to the model, runs whatever tools the model asks for, adds the results, and goes around again until the model is done.

Every coding agent has a loop like this somewhere. What I like about Pi's is how little it does on its own. The whole thing is one function of about 160 lines, runLoop, plus helpers for running tools. It keeps no state between runs. You hand it a conversation, a list of tools, and a config object full of optional hooks, and it reports everything it does as a stream of events.

All the clever parts of Pi (saving sessions, compaction, retries, plugins that block dangerous commands) live outside the loop and plug into those hooks. That keeps the loop easy to read and easy to trust.

One more thing worth knowing up front: the loop works with AgentMessage, which can include app-specific message types. It only turns them into plain LLM messages at the last moment, right before calling the model.

#Contracts

You don't need every type to follow the loop. These are the ones the pseudocode below uses, cut down to the fields that matter. Skipped fields are listed in a comment at the end of each type.

What the loop gets: a conversation, the tools it may run, and a function that calls the model.

type AgentContext = {
    messages: AgentMessage[],      // the conversation; apps can add their own message types
    tools: AgentTool[]?,           // the tools the loop is allowed to run
}

type StreamFn = (model, context, options?) -> AssistantMessageEventStream
    // never throws: a failure ends the stream with stopReason "error" or "aborted"

Tools. A tool is a name, a description, and a JSON schema for its arguments (that's the Tool part), plus an execute function.

type AgentTool = Tool & {
    execute: async fn(toolCallId, params, signal?, onUpdate?) -> AgentToolResult,
    executionMode: "sequential" | "parallel" ?,    // "sequential" makes the whole batch run one by one
    // skipped: label, prepareArguments, outputSchema, replay
}

type AgentToolResult = {
    content: (TextContent | ImageContent)[],       // what the model sees
    isError: Bool?,                                // report a failure without throwing
    terminate: Bool?,                              // hint: stop after this batch of tools
    // skipped: details, structuredContent, usage (extra data for the UI and for code, never sent to the model)
}

Hooks. Every hook is optional. This is where the host plugs in.

type AgentLoopConfig = {
    model: Model,
    convertToLlm: fn(AgentMessage[]) -> Message[],          // turn app messages into plain LLM messages
    getApiKey: fn(provider) -> String? ?,                   // asked before every request
    getSteeringMessages: async fn() -> AgentMessage[] ?,    // what the user typed mid-run
    getFollowUpMessages: async fn() -> AgentMessage[] ?,    // what waits until the agent would stop
    beforeToolCall: async fn(call, signal) -> { block?, reason?, terminate? } ?,
    afterToolCall: async fn(call, signal) -> AfterToolCallResult? ?,   // each field it returns replaces the old one
    finishTurn: async fn(turn, signal) -> { action: "continue" | "end" }? ?,
    toolExecution: "sequential" | "parallel" ?,             // default "parallel"
    // skipped: transformContext, prepareRequest, prepareNextTurn (they swap the context or model
    //          between requests), and the usual stream options like apiKey and reasoning
}

Events. A turn is one reply from the model plus the tools it called. A run is everything from one prompt until the loop stops, which can be many turns.

type AgentEvent =
    agent_start | agent_end { messages }               // agent_end is always the last event
  | turn_start  | turn_end { message, toolResults }
  | message_start | message_update | message_end      // message_update streams the model's reply
  | tool_execution_start | tool_execution_update | tool_execution_end { result, isError }

Entry points.

fn agentLoop(prompts, context, config, signal, streamFn) -> EventStream<AgentEvent, AgentMessage[]>
fn agentLoopContinue(context, config, signal, streamFn) -> EventStream<AgentEvent, AgentMessage[]>
    // runAgentLoop and runAgentLoopContinue do the same, but report events to a callback
async fn runToolCall(toolCall, options) -> AgentToolCallOutcome   // one tool call, for tools that call tools

#runAgentLoop

Sourceagent-loop.ts › runAgentLoop › agentLoop

This is where a run starts. It adds the new prompt to the conversation, tells listeners about it, and hands off to the main loop. agentLoop does the same thing but gives you the events as a stream you can iterate over.

async fn runAgentLoop(prompts, context, config, emit, signal, streamFn) -> AgentMessage[]
    initial = declareToolChanges(context, prompts)
    newMessages = copy of initial
    current = context with messages = context.messages + initial
    emit agent_start
    emit turn_start
    for each message in initial:
        emit message_start{message}
        emit message_end{message}
    await runLoop(current, newMessages, config, signal, emit, streamFn or getDefaultStreamFn())
    return newMessages

#runAgentLoopContinue

Sourceagent-loop.ts › runAgentLoopContinue › agentLoopContinue

Picks up where the conversation left off without adding anything new. Pi uses this to retry after an error.

async fn runAgentLoopContinue(context, config, emit, signal, streamFn) -> AgentMessage[]
    if context.messages is empty:
        throw Error("Cannot continue: no messages in context")
    if the last message is from the assistant:
        throw Error("Cannot continue from message role: assistant")
    newMessages = []
    emit agent_start
    emit turn_start
    await runLoop(copy of context, newMessages, config, signal, emit, streamFn or getDefaultStreamFn())
    return newMessages      // only what this run added

#applyNextTurnUpdate

Sourceagent-loop.ts › runLoop inline

This runs at the start of every turn after the first. It's the host's chance to swap in a new conversation (say, after compacting old history), switch models, or add messages before the next request.

fn applyNextTurnUpdate()
    update = config.prepareNextTurn?(lastCompletedTurn)
    if update:
        context = update.context or context
        prepared = update.messages or []
        config.model = update.model or config.model
        config.reasoning = update.thinkingLevel, with "off" meaning none
    if pending is empty:
        pending = config.getSteeringMessages?() or []
        // why: preparing can be slow (compaction calls the model), so pick up anything typed meanwhile.
        //      Only poll if the earlier poll was empty, or "one at a time" mode would deliver two.
    emit turn_start

#runToolBatch

Sourceagent-loop.ts › runLoop inline

Runs all the tool calls from one reply and adds their results to the conversation.

fn runToolBatch(message) -> (ToolResultMessage[], Bool)
    toolCalls = the toolCall blocks in message.content
    if toolCalls is empty:
        return [], false
    if message.stopReason is "length":
        batch = failToolCallsFromTruncatedMessage(toolCalls, emit)
    else:
        batch = executeToolCalls(context, message, config, signal, emit)
    add batch.messages to context.messages and newMessages
    return batch.messages, not batch.terminate

#declareToolChanges

Sourceagent-loop.ts › declareToolChanges › withToolChanges

In Pi, the tool list isn't a separate request field. It lives in system messages inside the conversation. So before each request, the loop compares the tools it can actually run with the tools the conversation has announced, and writes down the difference as toolsAdded / toolsRemoved on a system message.

fn declareToolChanges(context, pendingMessages) -> AgentMessage[]
    pendingSystem = the last system message in pendingMessages, if any
    baseline = pendingMessages, with pendingSystem's tool fields cleared
    changes = transcript.getToolStateChanges(            // transcript helpers live in pi-ai
        transcript.getCurrentTools(context.messages + baseline),
        context.tools mapped with transcript.toToolDeclaration)
    if pendingSystem exists:
        if there are no changes and pendingSystem declares none:
            return pendingMessages               // leave the caller's message alone
        return baseline with pendingSystem's tool fields set to changes
        // why: a pending system message's tool fields are only intent. Replace them with the
        //      real difference, so replaying the conversation gives exactly context.tools.
    if there are no changes:
        return pendingMessages
    insert a new system message {content: "", toolsAdded, toolsRemoved}
        before the first non-system pending message

#streamAssistantResponse

Sourceagent-loop.ts › streamAssistantResponse

Calls the model and turns its stream into agent events. This is the one place where agent messages become plain LLM messages.

async fn streamAssistantResponse(context, config, signal, emit, streamFn) -> AssistantMessage
    messages = config.transformContext?(context.messages, signal) or context.messages
    llmContext = transcript.normalizeContext({ messages: config.convertToLlm(messages) })
    apiKey = config.getApiKey?(config.model.provider) or config.apiKey
        // why: OAuth tokens can expire during a long run, so ask again before every request
    response = streamFn(config.model, llmContext, config + {apiKey, signal})
    for each event in response:
        match event.type:
            "start":
                push event.partial onto context.messages
                emit message_start{partial}
            text_*, thinking_*, toolcall_*:
                replace the last message with event.partial
                emit message_update{partial, event}
            "done", "error":
                final = response.result(), tagged with the thinking level we asked for
                put final in place of the partial (or add it, with message_start, if no "start" came)
                emit message_end{final}
                return final
    // if the stream just ends: finish up the same way

#failToolCallsFromTruncatedMessage

Sourceagent-loop.ts › failToolCallsFromTruncatedMessage

Used when the model ran out of output tokens in the middle of its reply. Its tool call arguments were rebuilt from cut-off JSON, so they might look fine but be missing something. Pi doesn't take the chance. It runs none of them and tells the model why.

async fn failToolCallsFromTruncatedMessage(toolCalls, emit) -> ExecutedToolCallBatch
    for each toolCall in toolCalls:
        emit tool_execution_start
        result = error "Tool call "<name>" was not executed: the response hit the
                 output token limit, so its arguments may be truncated. Re-issue ..."
        emit tool_execution_end{isError: true}
        emit message_start / message_end for the tool result
    return { messages, terminate: false }        // the model gets another turn to try again

#executeToolCalls

Sourceagent-loop.ts › executeToolCalls › executeToolCallsSequential

Decides between running tools one at a time or all at once. In sequential mode, each call finishes completely before the next one starts.

async fn executeToolCalls(context, assistantMessage, config, signal, emit) -> ExecutedToolCallBatch
    if config.toolExecution is "sequential" or any called tool has executionMode "sequential":
        return executeToolCallsSequential(...)
    return executeToolCallsParallel(...)

async fn executeToolCallsSequential(...)
    for each toolCall:
        emit tool_execution_start
        prep = prepareToolCall(context, assistantMessage, toolCall, config, signal)
        if prep is immediate:
            finalized = prep.result
        else:
            executed = executePreparedToolCall(prep, signal, onUpdate = emit tool_execution_update)
            finalized = finalizeExecutedToolCall(context, assistantMessage, prep, executed, config, signal)
        emit tool_execution_end
        emit message_start / message_end for the tool result
        if the run was aborted: break
    return { messages, terminate: shouldTerminateToolBatch(finalized) }

#executeToolCallsParallel

Sourceagent-loop.ts › executeToolCallsParallel

The default. Every call is checked first, one by one and in order (so beforeToolCall sees them in the order the model asked). Then the allowed ones run at the same time.

async fn executeToolCallsParallel(context, assistantMessage, toolCalls, config, signal, emit)
    entries = []
    for each toolCall in toolCalls:
        emit tool_execution_start
        prep = prepareToolCall(context, assistantMessage, toolCall, config, signal)
        if prep is immediate:
            emit tool_execution_end
            entries.add(prep.result)
        else:
            entries.add(run later:
                if aborted: result = error "Operation aborted"
                else: execute, then finalizeExecutedToolCall
                emit tool_execution_end)          // in the order the tools finish
        if the run was aborted: break
    outcomes = run all the "later" entries at once, keeping the original order
    for each outcome in outcomes:
        emit message_start / message_end for its tool result   // in the order the model asked
    return { messages, terminate: shouldTerminateToolBatch(outcomes) }

#prepareToolCall

Sourceagent-loop.ts › prepareToolCall › prepareToolCallArguments

Finds the tool, checks the arguments, and asks beforeToolCall whether the call is allowed. If anything goes wrong, you get an error result back, never an exception.

async fn prepareToolCall(context, assistantMessage, toolCall, hooks, signal, tools = context.tools)
        -> PreparedToolCall | ImmediateToolCallOutcome
    tool = tools.find(name == toolCall.name)
    if no tool:
        return immediate error "Tool <name> not found"
    try:
        call = toolCall with arguments = tool.prepareArguments?(arguments)
        args = validateToolArguments(tool, call)          // pi-ai: JSON schema check
        before = hooks.beforeToolCall?({assistantMessage, toolCall, args, context}, signal)
        if aborted:
            return immediate error "Operation aborted"
        if before.block:
            return immediate error (before.reason or "Tool execution was blocked"),
                   with terminate = before.terminate
        return prepared { toolCall, tool, args }
    catch e:
        return immediate error e.message

#executePreparedToolCall

Sourceagent-loop.ts › executePreparedToolCall

Runs the tool and times it. Progress updates are passed on only while the tool is still running.

async fn executePreparedToolCall(prepared, signal, onUpdate) -> ExecutedToolCallOutcome
    start a timer
    try:
        result = prepared.tool.execute(id, args, signal, onUpdate while still running)
        stop taking updates, wait for the ones already sent
        return { result, isError: result.isError == true, durationMs }
    catch e:
        stop taking updates, wait for the ones already sent
        return { error result e.message, isError: true, durationMs }

#finalizeExecutedToolCall

Sourceagent-loop.ts › finalizeExecutedToolCall

Gives afterToolCall a chance to rewrite the result. Any field it returns replaces the old one completely; there's no deep merge.

async fn finalizeExecutedToolCall(context, assistantMessage, prepared, executed, hooks, signal)
    result, isError = executed.result, executed.isError
    try:
        after = hooks.afterToolCall?({assistantMessage, toolCall, args, result, isError, context}, signal)
        if after:
            result.content, details, usage, terminate = after's value or the old one
            if after.structuredContent is set: use it
            else if after.content is set: drop structuredContent   // why: it may not match the new content
            isError = after.isError or isError
    catch e:
        result, isError = error result e.message, true
    return { toolCall, result, isError, durationMs: executed.durationMs }

#runToolCall

Sourceagent-loop.ts › runToolCall

Runs a single tool call through the same steps as a call from the model, but without events or new messages. It's for tools that call other tools, so things like permission checks in beforeToolCall still apply to them.

async fn runToolCall(toolCall, options) -> AgentToolCallOutcome
    prep = prepareToolCall(options.context, options.assistantMessage, toolCall, options, signal, options.tools)
    if prep is immediate:
        return { toolCall, prep.result, prep.isError }
    executed = executePreparedToolCall(prep, signal, options.onUpdate or nothing)
    return finalizeExecutedToolCall(..., prep, executed, options, signal)

#Rules

These are promises the loop keeps every time, whichever path a run takes. If the code ever stopped doing one of these, that would be a bug. MUST means always, MUST NOT means never, and SHOULD means "normally, unless there's a good reason".

MUST     emit agent_end as the very last event of every run
MUST     stop the run, without checking the queues, when a reply ends with "error" or "aborted"
MUST NOT run any tool call from a reply that stopped at the output token limit ("length")
         // why: its arguments were rebuilt from cut-off JSON and may be incomplete
MUST     run beforeToolCall for every call in the order the model asked, even in parallel mode
MUST     add tool results to the conversation in the order the model asked, even if tools finish out of order
MUST     emit tool_execution_end in the order tools finish, in parallel mode
MUST     run the whole batch one by one if any called tool asks for sequential execution
MUST     stop after a batch only when every result in it asks to stop (terminate = true)
MUST     add messages the user typed mid-run only after all tool calls of the current turn have finished
MUST     check follow-up messages only when there are no tool calls and no steering messages left
MUST     turn every tool failure (unknown tool, bad arguments, blocked, thrown, failing hook) into an error result
MUST NOT let a tool error escape from the loop
MUST     ignore progress updates a tool sends after it has finished
MUST     ask getApiKey for a key before every request          // why: short-lived OAuth tokens
MUST     convert agent messages to LLM messages only inside streamAssistantResponse
SHOULD   make at most one extra request when finishTurn asks to "continue"
MUST NOT continue from a conversation whose last message is from the assistant

  AND "first" takes 20ms longer to finish

  AND the tool results are saved as tool-1, then tool-2
  AND turn_end lists tool-1, then tool-2

#Notes

The loop never puts the system prompt or the tool list in separate request fields. Both live in system messages inside the conversation, and declareToolChanges keeps them in step with the tools the loop can actually run. The upside is that a saved conversation can be replayed on its own, with no outside state.

There's also streamProxy in proxy.ts, a StreamFn for apps that send model calls through their own server. The server leaves out the partial message on every event to save bandwidth, and streamProxy rebuilds it on the client.
